 ReactOS win32k — Excessive Locking Analysis
 Date: 2026-05-29
 Branch: codefix/Ivy-bcom
 Scope: win32ss/user/ntuser (USER) and win32ss/gdi (GDI)
================================================================================

VERDICT
-------
Yes — win32k is heavily locked, and a meaningful fraction is more aggressive
than necessary. However, the core design (one big USER lock) is largely
INHERITED from NT's own USER architecture, not a ReactOS invention. The
genuinely "excessive" parts are:
  (a) lock GRANULARITY  — one global lock for all of USER,
  (b) an EXCLUSIVE-BY-DEFAULT bias on the reader/writer lock,
  (c) a structural rule that forces every callback path to be exclusive.


THE LOCKING ARCHITECTURE
------------------------
Two completely different schemes in the two halves of win32k:

  USER (win32ss/user/ntuser):
      ONE single global ERESOURCE — "UserLock".
      Whole-subsystem granularity.

  GDI  (win32ss/gdi/ntgdi):
      Per-object pushlocks (pobj->pushlock) + a few global list ERESOURCEs.
      Per-object granularity (fine, well-designed).

USER lock primitives — win32ss/user/ntuser/ntuser.c:241-261
    UserEnterShared()    -> ExAcquireResourceSharedLite(&UserLock, TRUE)
    UserEnterExclusive() -> ExAcquireResourceExclusiveLite(&UserLock, TRUE)
                            gptiCurrent = PsGetCurrentThreadWin32Thread();  <-- NOTE
    UserLeave()          -> ExReleaseResourceLite(&UserLock)

  => Every NtUser* system call serializes through one reader/writer lock.
     That single lock is the headline source of "excessive locking".

  IMPORTANT SUBTLETY: the global "gptiCurrent" is assigned ONLY on exclusive
  entry, not on shared entry. Any code path that reads gptiCurrent therefore
  CANNOT be safely demoted from exclusive to shared. This constrains item #2
  below (see "SAFE-DEMOTION CRITERIA").


IDENTIFIED EXCESSIVE-LOCKING PATTERNS
-------------------------------------
1. SINGLE GLOBAL USER LOCK (the big one)
   All of USER — windows, messages, input, timers, clipboard, focus, menus —
   is protected by ONE ERESOURCE. No per-desktop, per-window-station, or
   per-queue lock. Any exclusive holder blocks ALL USER activity process-wide.
   Modern Windows win32k broke this up; ReactOS still mirrors the NT4-era
   single-lock model.

2. EXCLUSIVE-BY-DEFAULT BIAS
   Across win32ss/user/ntuser/*.c:
       227 exclusive acquisitions (UserEnterExclusive / UserEnterCo)
        63 shared    acquisitions (UserEnterShared)
       ~78% exclusive.
   A reader/writer lock only buys concurrency if reads use SHARED mode; here
   the writer mode dominates, so the RW lock often behaves like a plain mutex.
   Hottest files lean almost entirely exclusive:
       callback.c 17/0, message.c 13/0, desktop.c 12/0,
       painting.c 10/0, input.c 7/0.

   Concrete smell — NtUserGetForegroundWindow (focus.c:1643) reads a global
   pointer yet takes the EXCLUSIVE lock; compare NtUserGetDoubleClickTime /
   NtUserGetMonitorInfo / NtUserGetClassName, which correctly use shared.

3. CALLBACKS ARE STRUCTURALLY FORCED TO BE EXCLUSIVE
   UserEnterCo is hard-aliased to the exclusive lock (ntuser.h:3):
       #define UserEnterCo UserEnterExclusive
   There is NO shared callback variant. The callback pattern itself is correct
   (it drops the lock around the upcall — callback.c:204-212):
       UserLeaveCo();
       Status = KeUserModeCallback(...);
       UserEnterCo();          // always re-acquires EXCLUSIVE
   But because there's no UserEnterSharedCo, all 123 co_* functions are
   exclusive even when they only read.

4. GDI "SEMAPHORE" IS AN ALWAYS-EXCLUSIVE ERESOURCE
   EngCreateSemaphore allocates an ERESOURCE; EngAcquireSemaphore always takes
   it exclusively (win32ss/gdi/eng/semaphor.c:40-56). A shared variant exists
   (EngAcquireSemaphoreShared) but is used 6x vs 23x exclusive. Global lists
   ghsemPDEV / ghsemLDEVList / ghsemGraphicsDeviceList are each one global lock
   taken exclusively for walks that are mostly reads.

5. NESTED GLOBAL GDI LOCKS
   pdevobj.c:713-716 and dclife.c:555-586 acquire a per-PDEV lock AND the
   global ghsemPDEV (and lock two DCs' device locks in sequence). Multiple
   global locks held simultaneously is a contention / lock-ordering hazard.


WHAT IS *NOT* EXCESSIVE (to be fair)
------------------------------------
 - GDI per-object pushlocks (GDIOBJ_LockObject, gdiobj.c:833) are genuinely
   fine-grained, recursive per-thread, with a defined lock order. Well-designed.
 - Dropping the lock around usermode callbacks is REQUIRED for correctness
   (avoids holding a kernel lock across arbitrary user code). The churn is the
   price of safety, not a bug.
 - Many read-only queries DO correctly use UserEnterShared. The problem is
   inconsistency, not total absence.


SAFE-DEMOTION CRITERIA (for item #2 work)
-----------------------------------------
A UserEnterExclusive site may be demoted to UserEnterShared ONLY IF the body
between Enter and Leave:
   - does NOT call any co_* function (callback => must be exclusive),
   - does NOT call any mutator (Set/Create/Destroy/Add/Remove/Insert/Free/
     Alloc/Ref/Deref/Move/Update/Link/Unlink/...),
   - does NOT read the global gptiCurrent (set only on exclusive entry),
   - does NOT take a USER reference whose refcount update is non-atomic and
     relies on the exclusive lock,
   - only reads object/global fields and copies out to user mode.

Every candidate must be individually verified against the above; this is NOT a
mechanical search-and-replace.


RECOMMENDATIONS (payoff vs risk)
--------------------------------
1. LOW-RISK   : demote verified read-only UserEnterExclusive sites to shared.
                (NtUserGetForegroundWindow is a starter.)  <-- DONE / ~EXHAUSTED
                Batches 1-2 swept the entire read-only-NAMED exclusive pool
                (Get/Query/Enum/Find/Is, 15 funcs). Only 6 were genuinely safe;
                the rest are "Get" functions that lazily create/cache/destroy,
                take non-atomic USER refs, or call co_*. The low-risk well is now
                essentially dry — further wins require #2 or #3 below.
2. MEDIUM     : introduce UserEnterSharedCo so read-only callback paths stop
                forcing exclusive. (Unlocks GetScrollBarInfo, GetUpdateRect/Rgn
                with bErase=FALSE, and ~120 other co_* read paths.)  <-- NEXT
3. MEDIUM     : convert global GDI list walks to EngAcquireSemaphoreShared.
                (ghsemPDEV / ghsemLDEVList / ghsemGraphicsDeviceList — self-
                contained, no callback/refcount hazards. Best risk/reward.)
                <-- DONE / ~EXHAUSTED. Batch 3 swept all 10 exclusive sites on
                the 3 global locks; only 2 were pure reads (EngpFindGraphicsDevice,
                EngpGetPDEV). The other 8 are insert/unlink/teardown writers that
                must stay exclusive. The shared-walk well is now dry too.
4. HIGH/ARCH  : split UserLock into per-desktop / per-window-station locks.
                Real scalability fix, but invasive and regression-prone.

    - Multiple concurrent readers under shared do not conflict.
    - Any thread that could mutate/destroy the objects being read must take the
      EXCLUSIVE lock, which cannot proceed while a reader holds shared; so the
      raw (unreferenced) pointers stay valid for the read's duration.
    - The read helpers assert UserIsEntered(), which is satisfied by shared OR
      exclusive (ntuser.c:225-229), confirming they are designed for shared use.

    LDEVOBJ uses plain `pldev->cRefs++/--` (no Interlocked) — it genuinely relies
    on the exclusive lock for serialization, so it can NEVER be demoted. PDEVOBJ
    uses InterlockedIncrement/Decrement, which is why EngpGetPDEV's read+pin is
    demotable while LDEVOBJ_pLoadDriver's read+pin is not.

    - The fail-safe default (UserEnterExclusive) means any routine NOT explicitly
      whitelisted — including future additions — stays exclusive. Demotion is
      opt-in per verified routine, never by omission.

      so only the ACQUIRE needed splitting; the single Leave is unchanged.
    - Per-thread state is read via PsGetCurrentThreadWin32Thread()/GetW32ThreadInfo()

      the disqualifier that knocked out CLEAR/SETWINDOWSTATE etc.
