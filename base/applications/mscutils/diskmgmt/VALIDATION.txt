2026-07-22 ReactOS run notes
----------------------------
Topology: QEMU q35 + KVM, amd64 livecd (UEFI/OVMF), ich9-ahci with the
livecd ISO and a 4 GB blank qcow2 data disk (Disk 0), xHCI keyboard/mouse.

Validated natively end to end on the data disk: create primary 2048 MB FAT
(auto drive letter + quick format -> E: FAT32, 99% free), create logical
drive in the remaining space with auto-created extended container (-> F:
FAT32), delete primary, delete logical (free space reappears inside the
container), delete empty extended via its free space (primary survives),
automatic view healing after every operation with no manual refresh.

ReactOS issues found and fixed during this run (outside the app):
- partmgr.sys: DEVICE_RELATIONS allocation underflowed with 0 partitions
  (EnumeratedPartitionsTotal - 1), asking for 34 GB of paged pool and
  breaking PnP re-enumeration after deleting a disk's last partition.
- ntoskrnl xHalIoWritePartitionTable: with a >4-entry layout but no
  container partition, the EBR walk continued with a zero offset and
  rewrote sector 0 with an empty table, wiping the MBR (hardened; the app
  also clamps PartitionCount to 4 when it removes the container).

2026-07-23 follow-up: re-creating a partition with the same disk-signature/
offset/length identity as one removed earlier in the same boot session
bugchecked the kernel (PNP_DETECTED_FATAL_ERROR 0xCA, duplicate device
instance) once removal processing worked. Fixed in ntoskrnl
PiInitializeDevNode: the leftover phantom (DeviceNodeRemoved) devnode is
now retired so the re-arrived device takes over its identity; validated
in-VM with create -> delete -> identical re-create completing end to end
(letter + FAT32 quick format) in one boot. partmgr's SET-layout handlers
also got leak fixes and now propagate write failures to the caller.
