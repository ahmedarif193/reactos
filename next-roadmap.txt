1. FENCE-SPACE COLLAPSE  [ROOT CAUSE FOUND — FIXED IN TREE, NEEDS SILICON PASS]
   Three fence-mint sites in two counters sharing one numeric space:
     - tracked submits minted at KICK from adapter counter (vidsch.c:762 old)
     - untracked/ioctl submits minted at SUBMIT (d3dkmt.c:1852, adapter ctr)
     - untracked-with-0 + flip path minted from Engine->NextFenceId (2nd ctr!)
   Evidence (black boot): VidSch kick fences 2,3,4,5,6,125,126,131,132,388...
   while pending 98->885 never mass-drops: no packets lost — the counter was
   pumped ~118x between kicks by at-submit mints, so a kicked packet completes
   with a HIGHER fence than every UMD value handed out meanwhile -> threshold
   (miniport monotonic-max + vidsch retire + DMA-tracker signal) signals ALL of
   them -> UMD waits pass for work never executed. Cascade: gears free-runs,
   presents blit unrendered buffers (wsi mid-px=00000000 -> BLACK WINDOW),
   vidsch floods (885 pending), TDR ghost cycle every 2.28s, "38 FPS" fake.
   FIX (in tree): single adapter-wide counter minted at SUBMIT everywhere;
   explicit Packet->Kicked flag — retire/force-IDLE key on Kicked, never
   fence==0; NotifyInterrupt threshold now monotonic-max (no rewind).
2. CPU FENCE WAIT WAS A 100ms NAP  [FIXED IN TREE]
   DxgkSyncObjectCpuWait did ONE bounded 100ms KeWait and returned SUCCESS
   regardless of fence value (sync.c:681 old). Every "infinite" UMD wait
   (shim syncobj-wait tmo=INT64_MAX) degraded to <=100ms -> paced the fake
   33-38 FPS. FIX: loop until value reached (100ms re-check bound only for
   lost wakes; TDR guarantees advance). NonBlocking now returns STATUS_TIMEOUT
   when unreached.
   User-reported lines (added per request; all explained by this item +
   item 1, kernel fixes landed):
     shim: syncobj-wait #25 n=1 h0=7 flags=0x3 tmo=0
     shim: syncobj-wait #25 slot h=7 sig=0 fence=1
     shim: syncobj-wait #26 n=1 h0=8 flags=0x3 tmo=9223372036854775807
     shim: syncobj-wait #26 slot h=8 sig=0 fence=1
     shim: syncobj-wait #27 n=1 h0=9 flags=0x2 tmo=0
     shim: syncobj-wait #27 slot h=9 sig=0 fence=1
   Decode: "fence=1" prints HAS_FENCE (not the value); tmo=0 entries are
   vkGetFenceStatus polls returning ETIME (benign by design); the INFINITE
   (#26-style) waits returning early were the real bug — caused by the
   100ms-nap CpuWait (item 2) + fence-space aliasing (item 1), both fixed
   and verified on silicon (kick #N == fence N; waits now block).
3. V3D STALLS — NARROWED ON SILICON (batch-4 boot): 11 consecutive clean
   frames, real 35.6 FPS animation, 4 TDRs total of which the ONLY organic
   one is a DETERMINISTIC PT_INVALID MMU fault: VIO_ADDR=01704030 every
   boot, binner halted at BCL+0x10b (GL_SHADER_STATE region). VIO is
   <<8-scaled (Linux semantics) => fault VA 0x1_7040_3000 = a legit slab
   byte-address 0x01704030 read through a PACKED addr[39:8] field, i.e.
   v3dv wrote a full byte address where the hw wants addr>>8 (or the
   record misalignment equivalent). The other TDRs are aftershocks: first
   render after a core reset loses completion (reset_control parity gap).
   Forensics in tree: BCL+0x100..0x130 dump + 32B @VIO target dump on
   fault TDRs. Fix the packed field -> plausibly ZERO-TDR boots.
   (Also landed earlier: render-side invalidate before every CT1 kick,
   Linux parity; writer+kick DSBs.)
   With sync now honest this becomes THE visible blocker again (2.2s TDR per
   stall). Refined evidence (black boot dumps): CT1CS=0x10 (CTRUN) with CT1CA
   parked at RCL+0x01 / +0x4c / +0x86, PCS=0 or 4, CT0 fully consumed
   (CA==EA), MMU clean, isr=0, BFC advances (bin ran) RFC frozen; post-reset
   renders DO sometimes complete for real (RFC=1, TFU out shows red gears at
   fence 125/126/388+). Park offsets suggest CLE stalled in early RCL packets
   (config 0x79 blob / wait-on-semaphore 0x08) — decode TDR RCL byte dumps
   against v3d_packet.xml. Also compare Rpi5V3dResetCore vs linux v3d_reset
   (we SMS-pulse only; linux adds reset_control + full init_hw_state).
4. V3D IRQ dead: bcm2712.dtsi shows v3d has TWO lines <GIC_SPI 250>,<GIC_SPI
   249> (core+hub pair) and the 2712 GIC is a GIC-400 (v2). We only connected
   INTID 282 (SPI 250) — likely the wrong half of the pair. [IN TREE batch-7:
   both lines connected, same ISR; isr counter identifies the live one.]
   Timer res forced to 1ms (ExSetTimerResolution) since batch-6.
   Debate rematch verdict on the render park (item 3): H-A invalidate-discard
   and H-B missing-init-reg REFUTED at source (Linux does the identical
