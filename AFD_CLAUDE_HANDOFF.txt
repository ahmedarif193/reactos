PROVEN FAULT LOCATION
---------------------

The log loaded AFD at:

    afd.sys base = FFFF98DB164CC000

Bugcheck parameter 4 is:

    FFFF98DB164D8044 = afd.sys + 0xC044

That is exactly:

    AfdSelect+0x234
    drivers/network/afd/afd/select.c:326

Source:

    PollReq->Handles[i].Status =
        PollReq->Handles[i].Events & FCB->PollState;

Generated ARM64 instruction at afd.sys+0xC044:

    ldr w9, [x22, #0x240]

The instruction sequence loads x22 from FileObject->FsContext. DWARF confirms
AFD_FCB.PollState is at offset 0x240. Since the fault address is exactly 0x240,
FileObject->FsContext was NULL.

The GDB fallback later showing EarlyUartGetc is not the original fault. It
attached after the bugcheck while KDBG was polling the serial console. The
trustworthy evidence is the bugcheck tuple, loaded AFD base, exact offset,
generated instruction and KDBG AfdSelect frame.

LIKELY ROOT CAUSE TO PROVE
--------------------------

drivers/network/afd/afd/lock.c:319 LockHandles currently calls:

    ObReferenceObjectByHandle(..., FILE_ALL_ACCESS, NULL, KernelMode, ...)

It accepts any kernel object type, stores it as a handle/object pointer, and
AfdSelect later blindly casts it to PFILE_OBJECT and dereferences FsContext.
It neither requires *IoFileObjectType nor verifies that the file object belongs
to the AFD device and has a valid AFD context.

A multithreaded socket close/handle-reuse race can therefore turn one handle in
a select set into an event or another file object after user-mode validation.
The first socket still dispatches IOCTL_AFD_SELECT to AFD; a later mixed handle
is referenced as an arbitrary object and then treated as an AFD file object.

Do not implement a bare `if (!FCB) continue` workaround. The correct direction
is to validate and reject a non-AFD object before AfdSelect evaluates the set,
returning the Windows-observed failure status and releasing all references.
The exact NTSTATUS still needs the native discovery run described below.

----------------------------------------------------------

invalid handle. A clean implementation may need either:

    NTSTATUS LockHandles(..., PAFD_HANDLE *LockedHandles)

or an additional PNTSTATUS output. Pass the expected AFD PDEVICE_OBJECT into
the helper so it can validate FileObject->DeviceObject before any FCB access.
Do not accept a generic file object merely because FsContext is non-NULL.

FileObject->FsContext dereference at DISPATCH_LEVEL. The initial validation and
held file-object reference may make it safe, but cancellation/close ownership
must be checked rather than patched independently by guessing.
