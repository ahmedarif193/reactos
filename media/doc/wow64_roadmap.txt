ReactOS AMD64 WoW64 Roadmap
==========================

Context
-------
- Current amd64 builds still execute only native 64-bit user-mode binaries.
- Kernel structures already have placeholders (for example `struct _WOW64_PROCESS` in ntoskrnl/include/internal/ke.h) but they are unused.
- No wow64-specific user-mode modules (wow64.dll, wow64cpu.dll, wow64win.dll) are present in dll/win32.
- System call helpers such as `PsWrapApcWow64Thread` remain unimplemented stubs.

Guiding Goals
-------------
1. Run unmodified 32-bit Windows binaries on top of the amd64 ReactOS kernel.
2. Reuse the existing x86 ReactOS userland where possible (32-bit ntdll/kernel32/etc.).
3. Stay binary-compatible with the Windows WoW64 ABI so that third-party 32-bit installers and debuggers continue to work.
4. Keep the solution self-hosted (no dependency on a POSIX layer or Wine loader assumptions).

Architecture Outline
--------------------
A. Kernel support layer
   - Define `WOW64_PROCESS`/`WOW64_THREAD` runtime state: pointers to 32-bit PEB/TEB, user-mode address limits, pending APC bookkeeping.
   - Extend process creation to clone both native (64-bit) and compatibility (32-bit) PEB/TEB pairs, and to populate `EPROCESS->Wow64Process`.
   - Provide helper exports (`PsGetProcessWow64Process`, `PsGetCurrentProcessWow64Process`, `PsWrapApcWow64Thread`, context swap helpers) for wow64.dll.
   - Update trap handling to recognize compatibility segments and to hand off faults to the wow64 dispatcher before raising exceptions.
   - Ensure the memory manager publishes the 32-bit view (`MM_HIGHEST_USER_ADDRESS_WOW64`, `MM_SYSTEM_RANGE_START_WOW64`) via SharedUserData.

B. CPU transition helpers (wow64cpu.dll)
   - Implement switch stubs for `CpupReturnFromSimulatedCode`, `CpupDoCallBack`, `CpupDispatchException`, etc., using AMD64 `sysret`/`syscall` sequences.
   - Manage saving/restoring 32-bit register state inside the 64-bit TEB and vice versa.

C. NT system service thunking (wow64.dll)
   - Host the wow64 `THREAD_INFORMATION_BLOCK` (TIB) and dispatch table copied from the native PEB.
   - Translate 32-bit system call IDs and input structures into 64-bit `Nt*` calls; return results while applying pointer/size fixups.
   - Manage 32-bit APC delivery and user-mode callbacks through `PsWrapApcWow64Thread`.

D. Win32k thunking (wow64win.dll)
   - Convert win32k/syscall packets (`NtUser*`, `NtGdi*`) between 32-bit and 64-bit layouts.
   - Deliver message loops, input queues, and shared memory sections using 32-bit views.

E. Support libraries and environment
   - 32-bit `ntdll`, base DLLs, and 32-bit side-by-side assemblies must remain buildable and packaged under `\Windows\SysWOW64`.
   - File system and registry redirection helpers (wow64log.dll, optional) for installers and legacy APIs.

Execution Roadmap
-----------------
Phase 0 – Tooling & Build Foundations
   - Fix amd64 build scripts so both 32-bit and 64-bit sysroots are generated in the same build pass.
   - Teach the packaging scripts to snapshot the 32-bit user-mode tree into `system32`/`SysWOW64` layouts.

Phase 1 – Kernel Scaffolding
   - Flesh out `struct _WOW64_PROCESS` to hold 32-bit PEB base, TLS descriptors, and loader state pointers.
   - Implement allocation/free routines for wow64 state during `PspCreateProcess`/`PspDeleteProcess`.
   - Finish `PsWrapApcWow64Thread` and add accessor exports (`ntoskrnl/ntoskrnl.spec`).
   - Audit AMD64 trap handling (e.g. `KiGeneralProtectionFaultUserMode`) to branch into wow64-aware paths.

Phase 2 – Initial wow64cpu.dll
   - Port the context switch stubs from the ReactOS x86 kernel (`context.S`, `usercall.S`) into an amd64-friendly assembly module.
   - Expose entry points consumed by Windows wow64.dll (mirroring the public exports list).
   - Validate through unit tests that round-tripping thread contexts preserves flags/FPU state.

Phase 3 – Minimal wow64.dll Skeleton
   - Create `dll/win32/wow64` with a CMake target and stub implementations for loader/bootstrap routines (`Wow64LdrpInitialize`, `Wow64AllocateTemp`, etc.).
   - Implement the CSR handshake so that win32k-aware processes enter through `wow64.dll` rather than native `ntdll`.
   - Provide syscall thunks for a tiny subset required to run `cmd.exe` (e.g. `NtQueryInformationProcess`, `NtReadFile`, `NtWriteFile`).

Phase 4 – Win32 Thunk Expansion (wow64win.dll)
   - Add message, window, and GDI thunks sufficient for USER32/GDI32 initialization.
   - Hook into `win32k` to translate shared info structures (ATOM tables, handle tables) between 32- and 64-bit.

Phase 5 – Compatibility Services
   - Implement registry reflection/redirection (KEY_WOW64 flags) end-to-end.
   - Add filesystem redirection (`SysWOW64` ↔ `System32`) plus disable/reenable APIs.
   - Wire up the 32-bit loader policy (KnownDLLsWOW64, SxS manifests) inside the boot registry hive.

Phase 6 – Hardening & Validation
   - Grow syscall and win32 thunk coverage toward the Windows Server 2003+ surface area.
   - Add rostests/winetests coverage executed under wow64 to detect regressions.
   - Enable CI scenario booting a 64-bit VM and launching 32-bit userland smoke tests.

APC Dispatch Follow-up Checklist
--------------------------------
1. Implement the compat-mode trampoline (wow64cpu assembly) that pivots from the staged `WOW64_CONTEXT` into 32-bit execution and hands control back through `CpupReturnFromSimulatedCode`.
2. Wire `Wow64CpuDispatchPendingApc` into the real transition so that we drop the temporary `STATUS_NOT_IMPLEMENTED` return path and allow multiple APCs without clobbering state.
3. Preserve/restore the 64-bit trap frame so multiple APCs can be processed without corrupting native state (host context snapshot now captured prior to dispatch; restoration still pending).
4. Hook the dispatcher into the 32-bit TEB/TLS helpers so user-mode APC queues are serviced during alertable waits (`NtTestAlert`, `SleepEx`, etc.).
5. Add rudimentary tests (or instrumentation) that queue a user APC from 64-bit ntdll and confirm the 32-bit routine executes.

Current APC Dispatcher State
----------------------------
- `Wow64CpuDispatchPendingApc` snapshots the host `CONTEXT` and flips `APC_IN_PROGRESS` before asking the simulator to pivot; the cleanup path now releases the snapshot when `CpupReturnFromSimulatedCode` fires.
- `Wow64CpuSetPendingApc` publishes a kernel-style `WOW64_APC_CONTEXT`, so `wow64.dll` mirrors the Windows hand-off contract when it stages user-mode callbacks.
- `Wow64cpuSimulatePendingApc` still returns `STATUS_NOT_IMPLEMENTED`; the upcoming trampoline work must consume the staged compat/native contexts and actually jump into 32-bit code.
- `Wow64cpuApcTrampoline` now converts the staged compat frame into a native `CONTEXT`, stores the trio (compat/native/host) inside the CPU area, and forwards to a new `Wow64cpuExecuteCompatApc` stub that validates the captured state, clears the pending flags, and still awaits the real compat-mode jump.

Immediate Next Steps
--------------------
1. Stand up `wow64cpu` assembly glue that saves the 64-bit trap frame, loads the compat registers, and issues the transition to the 32-bit APC routine.
2. On return from the user routine, restore the captured host context (or convert back into a fresh native frame) and clear the pending APC bits.
3. Trace/instrument the new path so we can detect when the trampoline runs and diagnose failures without a debugger.

SysWOW64 Packaging Notes
------------------------
- Native amd64 binaries remain staged to `reactos/system32`; 32-bit companions must install into `reactos/SysWOW64` to mirror Windows layout.
- The amd64 build should stage the existing i386 userland tree during packaging so both architectures coexist on the boot media.
- Setup/packaging scripts need per-arch KnownDLL lists (64-bit under `system32`, 32-bit under `SysWOW64`) to keep loader search order predictable.
- MSI/installer compatibility depends on registry reflection (`HKLM\Software\Wow6432Node`) landing in the CD image; reserve that hive structure when generating bootcds.

CSR Bootstrap Outline
---------------------
1. Import `csrclient.dll` within wow64.dll and locate `CsrClientConnectToServer`, `CsrIdentifyAlertableThread`, `CsrSetPriorityClass`. (Requires kernel export of `PsWrapApcWow64Thread` for APC support.)
2. During `Wow64ProcessInit`, capture the native CSR connection handle from the 64-bit side and call `CsrClientConnectToServer(L"SmSsWin32")` to spawn the wow64 CSR thread block.
3. After connection, register the 32-bit thread context by calling `CpuProcessInit`/`CpuThreadInit` and stashing the CSR APIs that need wow64 marshaling.
4. On thread startup, `Wow64LdrpInitializeThread` must call `CsrIdentifyAlertableThread` and mark the thread with `PsWrapApcWow64Thread` so APC callbacks can traverse the 32-bit stack.
5. On termination, `Wow64ProcessTerm` has to call `CpuNotify(Wow64CpuNotifyShutdown)` followed by `CsrClientConnectToServer(NULL)` cleanup before the native process rundown.

Path to Running 32-bit Userland on AMD64 LiveCD
----------------------------------------------
Kernel & Executive
- Implement the compat APC trampoline body (`Wow64cpuExecuteCompatApc`) so it pivots into 32-bit mode and resumes via `CpupReturnFromSimulatedCode`.
- Guard exception/trap paths (e.g. `KiDispatchException`, user-call exit) to recognise WOW64 threads and hand off to wow64.dll instead of bugchecking.
- Ensure process/thread creation seeds PEB32/TEB32, loader parameters, and WOW64 flags; scrub them on teardown.
- Finish context APIs (`NtGetContextThread`, `NtSetContextThread`, `PsWrapApcWow64Thread`) for 32-bit callers running atop 64-bit threads.

wow64cpu.dll
- Port the AMD64<->x86 register shuffle assembly used for callbacks, syscalls, and exception unwinds (`CpupDoCallBack`, `CpupDispatchException`).
- Preserve FP/XMM state across transitions and synchronise with the kernel’s trap frame expectations.
- Add targeted tracing (guarded by DBG) so early LiveCD boots can diagnose transition bugs.

wow64.dll
- Expand bootstrap to drive CSR/LPC, KnownDLL resolution, and environment setup using the SysWOW64 tree.
- Implement the minimal syscall thunk set needed for console apps (`NtOpenFile`, `NtReadFile`, `NtQueryInformationProcess`, etc.).
- Wire TLS, APC delivery (`Wow64DeliverPendingApc`), and thread init/term so 32-bit ntdll behaves normally.
- Provide graceful fallbacks/logging when unimplemented thunks fire during bring-up.

GUI / win32k (optional milestone)
- Introduce wow64win.dll with enough USER32 thunks for window station & desktop creation, or explicitly gate GUI processes until this layer lands.
- Translate win32k packets (handles, shared info) between 32/64-bit layouts.

Packaging & Boot Media
- Finalise dual KnownDLL lists in hives, including 32-bit loader policy and SxS manifests.
- Mirror wow64*.dll, 32-bit base DLLs, and required side-by-side assemblies into `reactos/SysWOW64` during `ninja bootcd/livecd`.
- Update INF/CAB manifests so the LiveCD ships both architectures without duplicate conflicts.

Open Questions
--------------
- Should the first iteration target user-mode-only processes (CLI tools) before enabling USER32/GDI? This determines when wow64win.dll must be functional.
- How much of the thunk layer can reuse Wine sources versus clean-room reimplementation to stay close to NT behavior?
- Do we mirror Windows in requiring CPUID-based feature detection for wow64cpu, or can we assume long mode support across all amd64 hardware that boots ReactOS?
