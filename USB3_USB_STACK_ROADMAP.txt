ReactOS USB 3.x (xHCI) Support Roadmap
======================================

Legend:
- [ ] = not started
- [~] = in progress / partially done
- [x] = implemented / validated


Phase 1 – Basic SuperSpeed enumeration
--------------------------------------

1. EP0 descriptor flow and bMaxPacketSize0 handling
   - [x] In `drivers/usb/usbport/device.c` (`USBPORT_CreateDevice`), accept USB 3.x EP0 semantics:
     - For `DeviceDescriptor.bcdUSB >= 0x0300` and `bMaxPacketSize0 == 9`, treat EP0 MPS as 512 bytes.
   - [x] Ensure EP0 MPS (8 / 64 / 512) is propagated into:
     - `PipeHandle->EndpointDescriptor.wMaxPacketSize`
     - `Endpoint->EndpointProperties.MaxPacketSize` and `TotalMaxPacketSize`.
   - [x] In `drivers/usb/usbxhci/usbxhci.c`, confirm EP0 context uses the same MPS that USBPORT programs.

2. Control transfer length accounting
   - [x] In `XHCI_SubmitControlTransfer`, ensure `Transfer->RequestedLength` is set correctly based on:
     - `TransferParameters->TransferBufferLength` for data stages.
   - [x] In `XHCI_HandleTransferEvent`, verify:
     - `Remaining` is interpreted correctly for chained TRBs.
     - `BytesTransferred` matches what USBPORT expects, including short-packet cases.
   - [x] Re-test GET_DESCRIPTOR(DEVICE) on a SuperSpeed device:
     - First 8-byte read succeeds, second full 18-byte read succeeds.
     - `USBPORT_CreateDevice` no longer logs "TransferedLen - 8" errors and accepts bMaxPacketSize0.


Phase 2 – xHCI root-hub emulation
---------------------------------

3. Root-hub status and feature APIs in usbxhci
   - [x] Implement `XHCI_RH_GetStatus` to report hub-level status (no over-current / local power change by default).
   - [x] Implement `XHCI_RH_GetPortStatus` to:
     - Read `PORTSC` and fill `USB_PORT_STATUS_AND_CHANGE` (connect, enable, reset, over-current, etc.).
   - [x] Implement `XHCI_RH_GetHubStatus` to derive `USB_HUB_STATUS_AND_CHANGE` from port states.
   - [x] Implement `XHCI_RH_SetFeaturePort*` and `XHCI_RH_ClearFeaturePort*` in terms of `PORTSC`:
     - Reset, Power, Enable, Suspend, and their corresponding change bits.
   - [x] Make `XHCI_RH_DisableIrq` / `XHCI_RH_EnableIrq` mask/unmask the interrupter cleanly for root-hub use.

4. Port count and SuperSpeed vs non-SuperSpeed ports
   - [x] Use `HcsParams1` and `HcsParams2` to set:
     - `Extension->NumberOfPorts`.
   - [x] (Optional for now) If the controller exposes separate SS/root segments, reflect that into the root-hub model.


Phase 3 – USBPORT core USB 3 semantics
--------------------------------------

5. Speed handling
   - [x] Audit all uses of `USB_DEVICE_SPEED` (search for `UsbLowSpeed`, `UsbFullSpeed`, `UsbHighSpeed`).
   - [x] Add explicit handling for `UsbSuperSpeed`:
     - Device enumeration now derives `DeviceHandle->DeviceSpeed` from the USB 3.0 negotiated port speed on xHCI, so SuperSpeed devices are no longer treated as plain High‑Speed for EP0 and mapping.
     - Default control pipe creation on SuperSpeed now uses a 512‑byte EP0 max‑packet size, matching the bMaxPacketSize0==9 mapping.
     - [x] For High‑Speed devices (both on EHCI and xHCI), ensure EP0 `EndpointProperties.MaxPacketSize` is always 64 bytes as per the USB 2.0 spec; the 8‑byte “first GET_DESCRIPTOR” restriction is enforced only via the initial transfer length, not by programming an illegal EP0 MPS.
     - [x] When `DeviceSpeed` and the computed EP0 MPS are inconsistent with the spec (e.g. `UsbSuperSpeed` + MPS != 512, `UsbHighSpeed` + MPS != 64), have USBPORT fail enumeration early with a clear debug log instead of letting the xHCI miniport hit a `CONTEXT_ERROR` at Address Device time.
     - [x] Timeouts and retry logic for device reset/enumeration and initial auditing hooks for legacy quirks on SS devices.

6. Bandwidth and scheduling
   - [x] In the existing bandwidth accounting (bulk/iso/interrupt scheduling),
     - Short term: SuperSpeed endpoints now bypass the legacy USB 1.1/2.0 frame-based bandwidth pool in `USBPORT_AllocateBandwidth`, so they no longer consume from or fail due to the periodic bandwidth limits used for UHCI/OHCI/EHCI.
   - [x] Longer term:
     - Add distinct SS bandwidth model / constants (up to 5/10 Gbps, microframe-based).

7. Descriptor and pipe semantics
   - [x] Accept and ignore (for now) SuperSpeed Endpoint Companion descriptors on SS devices.
   - [x] Ensure class/protocol parsing does not misclassify SS devices (e.g., hubs, UVC, MSC).
   - [x] Align xHCI Address Device context with USBPORT’s EP0 semantics for HS/SS devices:
     - [x] In `XHCI_PrepareDefaultControlContext`, trust `Endpoint->EndpointProperties.MaxPacketSize` for EP0, and only assert/log on impossible combinations (e.g. HS with MPS != 64, SS with MPS != 512) instead of silently “fixing” MPS inside the miniport.
     - [x] In `XHCI_BringupDefaultControlEndpoint` / `XHCI_SendCommand`, when the controller returns completion code 5 (`CONTEXT_ERROR`) for Address Device, dump the slot/endpoint context words plus `PORTSC` and propagate a distinct miniport status back to USBPORT, so upper layers can see this as a context/descriptor problem rather than a generic `STATUS_INSUFFICIENT_RESOURCES`.


Phase 4 – USBHUB USB 3.0 awareness
----------------------------------

8. USB 3.0 hub descriptor support
   - [x] Introduce `USB_30_HUB_DESCRIPTOR` in the ReactOS headers based on Win10 `usbspec.h`.
   - [x] In `USBH_SyncGetHubDescriptor`, detect hubs with `bcdUSB >= 0x0300`:
     - Request the v3 hub descriptor using type 0x2A (with automatic fallback to 0x29 on failure).
     - Store SS-specific hub characteristics in the hub extension where needed.

9. Hub depth and route string
   - [x] Use the xHCI route string (`XHCI_BuildRouteString` + slot state) to:
     - Reflect hub depth and downstream port on USBPORT/USBD's view of the device.
   - [x] Ensure `HubAddr` / `PortNumber` in `USBPORT_ENDPOINT_PROPERTIES` match the xHCI route.

10. Port state handling
    - [x] Make `USBH_ProcessPortStateChange` able to handle USB 3 port states:
      - Link state (PLS), warm reset, and the SS-specific change bits from `PORTSC`.
    - [x] For now, keep U1/U2 disabled at the hub policy level.


Phase 5 – BOS and device capabilities
-------------------------------------

11. BOS parsing
    - [x] Add `USB_BOS_DESCRIPTOR` and the core device capabilities:
      - `USB_DEVICE_CAPABILITY_USB20_EXTENSION`.
      - `USB_DEVICE_CAPABILITY_SUPERSPEED_USB_DESCRIPTOR`.
      - `USB_DEVICE_CAPABILITY_CONTAINER_ID`.
    - [x] Implement BOS retrieval in `usbport`:
      - Issue GET_DESCRIPTOR(BOS) and parse the capabilities into the device handle.

12. Expose capabilities internally
    - [x] Store BOS-derived capabilities in the device extension for later IOCTLs and policy decisions.
    - [x] No immediate behavioral change required for LPM or container IDs in the first phase.


Phase 6 – Link Power Management (LPM, U1/U2/U3)
----------------------------------------------

13. LPM policy
    - [x] Add LPM-related fields (U1/U2 exit latencies, etc.) based on `usbspec.h`.
      - SuperSpeed BOS capability fields and per-device policy flags are now stored in `USBPORT_DEVICE_HANDLE`.
    - [x] Define a simple kernel policy:
      - A basic per-device LPM policy is computed in USBPORT from BOS data (U1/U2 exit latencies) and stored as U1/U2 allow flags; actual link-state programming and kill switch remain to be implemented.

14. LPM implementation in xHCI
    - [x] Program per-port U1/U2 enable bits in `PORTSC`/extended registers as per the xHCI spec.
    - [x] Ensure port/link state transitions are handled correctly in port-status and hub logic.


Phase 7 – Streams and advanced features (optional)
--------------------------------------------------

15. Bulk streams
    - [~] Extend `usbxhci` to manage stream-enabled bulk endpoints:
      - Create and manage stream contexts in the Endpoint Context and associated rings.
    - [~] Extend USBPORT’s internal endpoint representation to:
      - Track stream IDs and route completions accordingly.

16. UASP / enhanced MSC
    - [ ] Integrate with any future UASP miniport/class driver once streams are stable.


Phase 8 – IOCTL / user-mode compatibility
-----------------------------------------

17. IOCTL structure alignment
    - [x] Diff ReactOS `sdk/include/psdk/usbioctl.h` against Win10:
      - Import/update extended node connection info (`*_EX_V2`), especially SS-related fields.
    - [x] Implement IOCTL handlers in the USBPORT/USBD/USBHUB path:
      - Populate SS fields using BOS, hub descriptors, and xHCI port information.

18. Tooling verification
    - [x] Add a simple user-mode test app or extend existing tools to:
      - Enumerate devices and display SS/USB 3 attributes via IOCTLs.


Cross-cutting / maintenance
---------------------------

19. Debug and trace hygiene
    - [x] Keep xHCI DPRINT1 output focused on errors, with `DPRINT` for high-frequency traces.
    - [x] Add a debug switch to selectively enable verbose event-ring / TRB logging when needed.

20. Conformance and robustness
    - [~] Compare the behavior of this stack against Windows 10/11 on the same hardware (where possible):
      - Reset timing, retries, and error codes for common devices (HID, mass storage, hubs, webcams).
    - [x] Add assertions and graceful fallback paths in xHCI for unsupported hardware quirks.
