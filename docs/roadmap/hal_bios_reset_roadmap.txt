HAL Legacy Reset Stabilization Roadmap
=====================================

Context
-------
Recent testing exposed a release-only 0xD1 bug in the i386 HAL when
`HalResetDisplay` enters the legacy VGA BIOS reset path. The fast486/V86
helpers rely on stack-allocated trap frames that were not fully
initialised, leaving the release build vulnerable to optimiser-driven
corruption. A temporary workaround (using the debug HAL or skipping the
HAL reset) confirmed the fault is confined to this code path.

Objectives
----------
1. **Stabilise the existing BIOS reset sequence** so the free build boots
   reliably on legacy systems.
2. **Harden the HAL real-mode helpers** against similar optimisation
   issues.
3. **Audit adjacent low-level paths** (boot-time DMA, BIOS emulation,
   hardware initialisation) for comparable risks.
4. **Improve regression coverage** with scenarios that exercise legacy
   BIOS calls under release optimisation levels.

Milestones & Tasks
------------------

Milestone 1 – Immediate Fixes
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Zero-initialise the V86 trap frame, register snapshots and saved context
  before handing control to fast486 (`HalpBiosCall`).
- Review other structures touched by `HalpBiosDisplayReset` and ensure
  they are explicitly initialised.
- Restore safe default behaviour for `HalResetDisplay` on free builds and
  keep Bootvid fallbacks intact.

Milestone 2 – Broader HAL Audit
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Survey the HAL’s real-mode/V86 helpers for additional uninitialised or
  aliasing-sensitive state.
- Examine fast486 emulator entry/exit points for assumptions about stack
  layout or compiler behaviour; add `volatile`/barriers where required.
- Inspect boot-time DMA and scatter/gather paths that recently received
  extra trace instrumentation, verifying no debug-only assumptions remain.

Milestone 3 – Tooling & Testing
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Enable GCC/Clang warnings (`-Wuninitialized`, `-Wmaybe-uninitialized`)
  for HAL sources and triage new diagnostics.
- Integrate a release-config boot smoke test (e.g. QEMU-based) to catch
  regressions early.
- Add a static analysis sweep (Cppcheck/clang-tidy) focused on kernel/HAL
  modules touching real-mode or trap-frame logic.

Milestone 4 – Longer-Term Enhancements
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Evaluate replacing portions of the custom fast486 BIOS emulation with a
  better-tested component or constraining its usage to well-defined
  scenarios.
- Investigate PAE/high-memory enablement so we stop discarding physical
  memory beyond 2 GB on x86, ensuring any new HAL work coexists with that
  effort.
- Document best practices for interacting with the HAL’s legacy paths so
  future changes respect their constraints.

Deliverables & Tracking
-----------------------
- Bug fixes landed in-tree (HAL zeroing, logging cleanup, regression
  tests).
- Audit report that captures findings and outstanding risks from the
  broader review.
- Updated developer documentation covering the HAL reset path.

Ownership & Dependencies
------------------------
- *Primary owners:* HAL/ARM3 maintainers.
- *Dependencies:* fast486 emulator expertise, boot/FreeLDR maintainers for
  coordinating any shared data-structure changes.

Risk Management
---------------
- Applying zero-initialisation across sensitive structures mitigates the
  immediate crash but may mask deeper architectural issues; auditing keeps
  us honest.
- Release-only bugs are hard to validate; automated release-config tests
  are critical before declaring the roadmap complete.
