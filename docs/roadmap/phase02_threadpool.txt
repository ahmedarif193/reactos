Phase 02 – Vista Threadpool & Concurrency
=========================================
Goal: provide the full Vista threadpool API surface so higher-level components (CRT,
RPC, networking) can rely on the modern worker infrastructure. These exports currently
call Wine stubs, leading to loader crashes or runtime failures once Phase 01 is complete.

Functions to Implement
----------------------
Threadpool Creation & Destruction
- CreateThreadpool / CloseThreadpool
- CreateThreadpoolCleanupGroup / CloseThreadpoolCleanupGroup /
  CloseThreadpoolCleanupGroupMembers
- CreateThreadpoolWork / SubmitThreadpoolWork / WaitForThreadpoolWorkCallbacks /
  CloseThreadpoolWork
- CreateThreadpoolIo / StartThreadpoolIo / CancelThreadpoolIo /
  WaitForThreadpoolIoCallbacks / CloseThreadpoolIo
- CreateThreadpoolTimer / SetThreadpoolTimer / IsThreadpoolTimerSet /
  WaitForThreadpoolTimerCallbacks / CloseThreadpoolTimer
- CreateThreadpoolWait / SetThreadpoolWait / WaitForThreadpoolWaitCallbacks /
  CloseThreadpoolWait

Threadpool Configuration
- SetThreadpoolThreadMinimum / SetThreadpoolThreadMaximum
- TrySubmitThreadpoolCallback (needs fallback to CreateThreadpoolWork when convenient)
- SetThreadpoolCallbackPriority / SetThreadpoolCallbackRunsLong (if exposed via attributes)
- FreeLibraryWhenCallbackReturns / LeaveCriticalSectionWhenCallbackReturns /
  ReleaseMutexWhenCallbackReturns / ReleaseSemaphoreWhenCallbackReturns /
  SetEventWhenCallbackReturns

Infrastructure Helpers
- InitializeProcThreadAttributeList & related (if not already handled in Phase 01)
- CallbackMayRunLong – informs scheduler about long-running callbacks
- DisassociateCurrentThreadFromCallback – required for clean shutdown during cancel

Why These Matter
----------------
- Vista’s threadpool superseded the old NT worker queue; modern libraries (RPC, HTTP,
  CLR, libstdc++) rely on these semantics. Without them, applications may load but hit
  unimplemented stubs at first async operation.
- Winetest `kernel32:threadpool` already exercises many of these functions, so they’re
  necessary for test parity.

Implementation Strategy
-----------------------
1. Base Architecture: either port Wine’s `threadpool.c` implementation or build on top of
   ReactOS’s existing worker threads. Ensure callbacks execute in a controlled context and
   support cancellation tokens.
2. IO Completion: integrate with existing IOCP implementation. Maintain per-handle
   threadpool IO objects and call the registered callback when completions arrive.
3. Timers & Waits: use `RtlCreateTimerQueue` or implement a small timer wheel backed by
   `KeDelayExecutionThread`. Wait objects should register APCs when the watched handle is
   signalled.
4. Cleanup Semantics: ensure `CloseThreadpool*` waits for outstanding callbacks unless the
   caller specifies `TP_CALLBACK_ENVIRON_V3` flags.
5. Testing: expand winetests to cover cancellation, priority changes, and edge cases
   (e.g. destroying pools while callbacks pending). Add kernel32 APITESTs for regression.

Deliverables & Exit Criteria
----------------------------
- All threadpool exports removed from `docs/vista_stub_exports.txt`.
- `modules/rostests/winetests/kernel32/threadpool.c` passes on both x86 and amd64.
- Stress test: start a worker pool with thousands of callbacks; ensure no leaks or
  crashes under Application Verifier.
