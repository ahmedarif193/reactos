ReactOS Vista-Dev AMD64 Roadmap
================================

Purpose
-------
Build a consolidated plan that starts with reproducing the amd64 LiveCD setup hang, diagnoses the differences against the working i386 build, fixes the missing CRT/export issues that block shellbtrfs.dll, restores Vista-era API parity (e.g. GetProductInfo), and registers the outstanding COM classes (WMI refresher and TaskbarList) so setup stops failing with "class not registered".

Phase 0 – Environment & Baseline
--------------------------------
A. Toolchain parity
   1. Refresh host prerequisites (cmake, ninja, mingw-w64, nasm) and document exact versions used for previous successful i386 build.
   2. Cleanly reconfigure both targets from the ReactOS source root:
      - `configure.sh cmake -DENABLE_CCACHE=ON -DARCH=i386 -DENABLE_TESTS=OFF`.
      - `configure.sh cmake -DENABLE_CCACHE=ON -DARCH=amd64 -DENABLE_TESTS=OFF`.
   3. Capture `ninja --version`, toolchain paths, and environment diffs between the two build directories.
B. Logging hooks
   1. Enable verbose loader and COM traces by adding `set ROS_DBGCHANNEL=+load,+regsvc,+ole,+msi` before boot.
   2. For amd64, turn on KD serial logging (`bcdedit /set sos on`, `bcdedit /set debug on`) so stack exhaustion dumps are preserved.
   3. Verify LiveCD ISO creation succeeds for i386 to act as a control artifact.

Phase 1 – Reproduce the amd64 hang
----------------------------------
A. LiveCD boot sequence
   1. Boot the freshly built amd64 LiveCD under the same hypervisor parameters used for the working i386 case.
   2. Record the full log around timestamps 43–77s where the setup.exe failure occurs (shell32/advpack/urlmon stubs, w32time registration, msvcrt.wctob stub, message queue cleanup, stack exhaustion).
   3. Confirm whether the stack exhaustion crash repeats consistently and whether disabling shellbtrfs in `reactos.inf` changes behaviour.
B. Compare against i386
   1. Collect the same trace points on i386 to identify which warnings are common (shell32 stub traces) versus amd64-only (msvcrt.wctob, thread cleanup FFFFF8A000229F20, pagfault.c:122 fatal).
   2. Diff module dependency trees with `dumpbin /dependents` (or `llvm-readobj --dyn-symbols`) for shellbtrfs.dll between architectures to highlight missing exports on amd64.

Phase 2 – Fix the CRT export gap (msvcrt.dll wctob) [COMPLETED]
---------------------------------------------------------------
A. Root-cause validation
   1. Inspect `dll/win32/msvcrt/msvcrt.spec` to confirm `wctob` forwards to `ucrtbase.wctob` and that amd64 `dll/win32/ucrtbase` does not currently export an implementation.
   2. Check `sdk/lib/crt/string/btowc.c` and `sdk/lib/ucrt/convert/wcrtomb.cpp` to verify usable code already exists for both CRT flavours.
   3. Audit cmake targets to see whether the amd64 build of msvcrt links against the correct object providing `wctob` (look at `dll/win32/msvcrt/CMakeLists.txt`).
B. Code changes
   1. Either stop forwarding and expose an in-module implementation (add `msvcrt/wctob.c` that calls the shared helper from `sdk/lib/crt/string/btowc.c`) or ensure `ucrtbase` exports `wctob` for amd64 by compiling `sdk/lib/ucrt/convert/wcrtomb.cpp` into that DLL. **Done:** the forward was removed and `wctob` now exports directly from `msvcrt` on all architectures.
   2. Update corresponding `.spec` files (msvcrt.spec, ucrtbase.spec) to match Windows 6.0+ and adjust ordinal mappings. **Done:** `msvcrt.spec` now exports `wctob` without forwarding.
   3. Add an automated regression test in `modules/rostests/winetests/msvcrt/string.c` that runs on amd64 and exercises `p_wctob`. *Pending (follow-up once test plan is defined).* 
C. Validation
   1. Rebuild the amd64 CRTs, ensure `dumpbin /exports msvcrt.dll | find "wctob"` shows a non-stub entry.
   2. Reboot LiveCD; verify shellbtrfs.dll no longer fails during `DllMain` and that setup progresses past the previous hang.

Phase 3 – Harden shellbtrfs & loader interactions
-------------------------------------------------
A. Dependency audit
   1. Run `dumpbin /imports shellbtrfs.dll` (both arches) to ensure every dependency is available; pay attention to msvcrt/ucrt, shell32, shlwapi. **Done:** x64 import list reviewed; only `msvcrt.dll.wctob` was missing prior to Phase 2 and is now present.
   2. Review `dll/win32/shellbtrfs` sources for amd64-specific guards; confirm no code is still `#ifdef _M_IX86` only (notably inline assembly or pointer truncation). **Done:** no amd64-only gaps found.
B. Loader diagnostics
   1. Instrument `dll/win32/kernel32/client/loader.c` around `LoadLibraryExW` failure path to log NTSTATUS (already printing c0000142) and module dependency chain for the failing load. **Done:** failure logs now include module name, flags, characteristics, and search path.
   2. Add temporary asserts/logging in `dll/ntdll/ldr/ldrinit.c` to capture which export triggered the unimplemented stub callback. *Revisit later if more stub tracing is required; current dbgprints from `__wine_spec_unimplemented_stub` identify the culprit export.*
C. Follow-up fixes (if shellbtrfs still fails)
   1. Address any remaining amd64-only missing exports (expand `dll/win32/shell32/shell32.cpp` stubs if shellbtrfs expects real behaviour).
   2. Re-run setup to confirm absence of repeated `Thread Cleanup Post Messages` errors once LoadLibrary succeeds.

Phase 4 – Restore `ninja livecd` reliability
--------------------------------------------
A. Reproduce the build failure in `output-MinGW-amd64-Debug` using `ninja livecd`. **Done:** amd64 LiveCD builds cleanly after the CRT/COM updates.
B. Inspect `boot/CMakeLists.txt` and `media/CMakeLists.txt` for amd64 guard differences compared to i386; ensure livecd target depends on newly produced amd64 drivers (e.g. shellbtrfs64, new CRT DLLs). *No discrepancies observed; keep monitoring as new binaries land.*
C. Fix the build graph so required binaries are included (update `livecd.inf`, `reactos.inf`, and the LiveCD packing scripts under `boot/bootdata`). *Not required for the current fix set; follow up if future payloads are added.*
D. Add a CI script snippet (e.g. in `.azure-pipelines`) to run `ninja livecd` for amd64 to prevent regressions. *Open follow-up to extend CI coverage.*

Phase 5 – Vista-era API parity (kernel32 GetProductInfo)
--------------------------------------------------------
A. Confirm `dll/win32/kernel32/client/version.c` already implements `GetProductInfo` but the amd64 export is missing; inspect `dll/win32/kernel32/kernel32.spec` for the `-version=0x600+` guard. **Done:** implementation verified.
B. Update the export list so amd64 builds ship the function (remove incorrect `-version=0x600+` guard or ensure the spec is processed), and mirror in `kernelbase.spec`. **Done:** `GetProductInfo` now exports unconditionally from kernel32 and continues to forward through kernelbase.
C. Add a smoke test to `modules/rostests/winetests/kernel32/version.c` that only runs when the function is present, verifying it returns `TRUE` with valid output. **Done:** amd64 builds assert the export and exercise `GetProductInfo`.

Phase 6 – COM registration fixes (wbemdisp & browseui) [IN PROGRESS]
--------------------------------------------------------------------
A. WMI refresher classes
   1. Expand `sdk/include/psdk/wbemdisp.h` to define interfaces: ISWbemRefresher, ISWbemRefreshableItem, ISWbemRefreshableEnum, ISWbemRefreshableItemEx, ISWbemConfigureRefresher, plus enums (e.g. WbemRefreshFlagEnum). **TODO:** only forward declarations exist; import method signatures/DISPIDs/enum members from a captured Vista/Win7 `wbemdisp.tlb`.
      - `wbemdisp.idl` follow-up items:
        * Mirror the typelib attributes (helpstrings, dual flags, inheritance) for each missing interface once we have the authoritative source.
        * Add the Vista `WBEM_REFRESHER_FLAGS` enum and script-facing constants referenced by `ISWbemRefresher.Refresh`.
   2. `dll/win32/wbemdisp/refresher.c` roadmap:
      - Flesh out the IWbem/IWbemConfigure layers to proxy into `wbemprox` or the native WMI provider instead of returning `WBEM_E_NOT_SUPPORTED`.
      - Convert the current FIXME logging into proper TRACE-level instrumentation once functionality lands; keep a condensed WARN when we return stubs.
      - Implement `ISWbemRefreshableItem` accessors so scripting clients can read refreshed objects/sets (leveraging `wbemprox` once the backend is ready).
      - Add placeholder structures for `ISWbemRefreshableEnum`/`ISWbemRefreshableItemEx` so wiring them becomes drop-in once the headers are updated.
   3. `wbemdisp_classes.idl` / `.rgs` follow-up:
      - When new coclasses are introduced (SWbemRefreshableEnum, SWbemRefreshableItemEx, WbemConfigureRefresher), ensure matching ProgIDs and threading models are published.

   4. Validation tasks (after interface import):
      - Rebuild the tlb (`midl`) and verify exported interface IDs match a Windows reference dump (`oleview`/`tlibimp`).
      - Extend `modules/rostests/apitests/com/wbemdisp.c` to CoCreate the new CLSIDs once they are registered.
   2. Add the following CLSIDs/IIDs to `dll/win32/wbemdisp/guid.c` and headers:

      - CLSID_SWbemRefresher `{D269BF5C-D9C1-11D3-B38F-00105A1F473A}`.
      - CLSID_SWbemRefreshableItem, CLSID_SWbemRefreshableEnum, CLSID_SWbemRefreshableItemEx, CLSID_SWbemLocator (if missing). **Done:** GUID table now includes the refresher and refreshable item CLSIDs/IIDs.
   3. Implement minimal COM servers in new source files (e.g. `refresher.c`, `refreshable_item.c`) returning `E_NOTIMPL` but supporting class factory creation. **Done:** `refresher.c` provides stubbed IWbem*/ISWbem* implementations registered via the factory map, with `FIXME` traces on each unimplemented entry point.
   4. Extend `wbemdisp.spec`, `wbemdisp_classes.idl`, and `wbemdisp_classes.rgs` with the new coclasses and ProgIDs so `DllRegisterServer` writes full registry entries. **Done:** IDL and .rgs now describe SWbemRefresher/SWbemRefreshableItem and reference the native CLSID_WbemRefresher.
   5. Update `dll/win32/wbemdisp/CMakeLists.txt` to compile/include the new sources for both architectures. **Done:** build script now builds `refresher.c`.
   6. Add a smoketest that instantiates the new refresher classes so regressions surface quickly. **Done:** `com_apitest` now loads `wbemdisp.dll`, runs `DllRegisterServer`, and CoCreates `CLSID_WbemRefresher` / `CLSID_SWbemRefresher`.
B. TaskbarList and related browseui classes
   1. Verify `dll/win32/browseui/CTaskbarList.cpp` already implements ITaskbarList/ITaskbarList2. **Done:** implementation confirmed, no changes required.
   2.
